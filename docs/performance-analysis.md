# 3D 네비게이션 성능 영향 분석 보고서 (Future Version 참고)

## 📊 리소스 및 성능 분석

교수님, 매우 날카로운 질문입니다! 3D 기능을 도입하면 당연히 프로그램이 무거워질까 봐 걱정되실 수 있죠. 하지만 현대적인 기술(MapLibre GL JS)은 오히려 어떤 면에서는 효율적일 수도 있습니다. 비교 분석 결과를 정리해 드립니다.

### 1. 엔진 무게 (Bundle Size)
- **Leaflet (현재)**: 매우 가볍습니다 (약 40KB).
- **MapLibre (3D)**: 기능이 많은 만큼 조금 더 무겁습니다 (약 200KB~). 
- **소견**: 초기 로딩 시 아주 미세한 차이는 있지만, 현대의 네트워크 속도에서는 체감하기 어렵습니다.

### 2. 메모리 및 CPU/GPU 사용량
- **Leaflet**: CPU가 지도를 그리는 데 주력합니다. 이미지를 계속 가져와 보여주므로 CPU 부하가 적어 보이지만 확장에 한계가 있습니다.
- **MapLibre**: **GPU(그래픽 장치)**를 사용합니다. 3D 게임처럼 그래픽 카드를 사용하므로 화면 이동이나 회전이 **훨씬 더 부드럽습니다(60FPS).**
- **소견**: 저휘도 및 저사양 기기에서는 배터리 소모가 약간 늘어날 수 있지만, 최신 스마트폰에서는 훨씬 쾌적한 경험을 줍니다.

### 3. 데이터 전송량 (Data Traffic)
- **Leaflet**: 수많은 이미지를 조각조각 다운로드합니다.
- **MapLibre**: **벡터 데이터**만 가져옵니다. 텍스트 데이터를 가져와서 기기가 직접 그리므로, **전체 데이터 전송량은 오히려 줄어들 수 있습니다.**

## 💡 최적화 전략 (안 무겁게 만드는 법)

1. **Lazy Loading**: 평소에는 지도를 로딩하지 않다가 '여행 안내'를 클릭할 때만 독립된 프레임(IFrame 등)에서 호출하여 메인 앱의 속도를 보존합니다.
2. **별도 프레임 운영**: 사용자가 말씀하신 대로 웹/앱과는 별개로 운영하면, 메인 서비스는 가볍게 유지되고 네비게이션이 필요한 순간에만 고사양 엔진이 가동됩니다.
3. **오프라인 타일**: 필요한 영역만 미리 벡터 데이터를 다운로드하여 저장(Caching)해 두면 통신 지연 없이 매우 빠르게 작동합니다.
